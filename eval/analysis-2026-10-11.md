# Alidade 评测分析报告（2026-10-11）

接着 [2026-10-10 的报告](analysis-2026-10-10.md)。这一轮做了五件事：

1. 用不含评测示例的提示词重测"先澄清"和数据体检；
2. 用模拟用户检验"先问"是不是真的更贴合用户想要的；
3. 测量计划随出图自动推进省了多少；
4. 测量并行子 Agent；
5. 修过度反问。

模型都是 `deepseek-flash`，结果目录都在 `eval/results/` 下。

## 1. 先澄清：用干净的提示词重测

上一份报告评测时，提示词里的几个示例和评测题直接对应，已在 2026-10-11 换掉，并加了测试防止再发生。这次用同一批题重测：13 道题 × 2 次。

- 改造前：`old-focus`
- 改造后：`new-focus-clean`
- 对比报告：`compare-focus-clean.md`

| 指标 | 改造前 | 改造后（干净提示词） | 上一份报告（提示词有泄漏） |
|---|---|---|---|
| 任务成功率 | 73% | 92% | 96% |
| 出图前先反问的比例（模糊/需澄清题） | 6% | 75% | 81% |
| 必须先澄清的题：做到的比例 | 17% | 67% | 83% |
| 用户确认方向前的平均 token | 84,425 | 38,958（−54%） | 43,106（−49%） |
| 数据清洗题成功率 | 80% | 100% | 100% |
| 明确问题中反问的比例 | 0% | 0% | 0% |

- **泄漏的影响：** 换掉示例后，"必须先澄清"从 83% 降到 67%，说明之前确实有一部分来自示例对上了题目。下降后仍比改造前高 50 个百分点。
- **数据体检：** 不受影响，两次都是 100%。
- **仍未解决的题：** `clarify-stocks-period`（"去年和今年表现差别最大的股票"）这一轮 4 次都没有先反问。没有针对它调提示词，以免对这道题过拟合。

## 2. 模拟用户："先问"是否真的更贴合用户想要的

**做法：**

- 8 道模糊/需澄清题各设一个隐藏的用户意图和对应答案。例如"最成功的电影"其实想看预算 ≥ 5000 万美元的电影里回报率最高的，答案是 Jurassic Park。
- Agent 反问时，由同一个模型扮演用户，按这个意图作答。
- 判分看结论是否答到这个意图。必须先澄清的题仍然要求在出图前先反问。
- 每题 2 次，每个版本 16 次运行。

结果目录：`old-usersim`、`new-usersim`；对比报告：`compare-usersim.md`。

| 指标 | 改造前 | 改造后 | 变化 |
|---|---|---|---|
| 按用户真实意图答对的比例 | 75% | 100% | +25 pp |
| ……其中没反问的运行 | 64%（7/11） | 100%（4/4） | |
| ……其中反问过的运行 | 100%（5/5） | 100%（12/12） | |
| 任务成功率（含"必须先澄清"的要求） | 50% | 88% | +38 pp |
| 出图前先反问的比例 | 6% | 75% | +69 pp |
| 平均总 token | 112,603 | 77,800 | −31% |
| 用户确认方向前的平均 token | 94,363 | 36,993 | −61% |
| 平均图表数 | 3.0 | 1.6 | −48% |
| 平均耗时（秒） | 37.8 | 32.1 | −15% |

**分析：**

- **改造前的 4 次失败都是"没问、猜错了"：**
  - 油价题画了 5 张全景图，没有比较柴油和普通汽油；
  - 能源题没有看核电下降；
  - 电影题没有按发行商比较口碑；
  - "最成功的电影"按票房回答。
- **只要问了，两个版本都答对了。** 差别在于改造前很少问。它问过的 5 次里有 4 次是先画了 1–5 张图才问，花的 token 最多（最高 25.7 万）。
- **总 token 明显下降。** 上一份报告里，自动选推荐选项时总 token 是 +13%；这次换成按用户意图回答，总 token −31%。因为改造后问清楚就只画用户要的那 1–2 张，改造前要先把能想到的角度都画一遍。所以"先问"不只是方向更准，也更省。
- **改造后没问的 4 次也答对了：** `unemp-ambiguous` 和 `clarify-stocks-period` 各 2 次。改造前这两道题不问也都答对了，说明它们的意图比较好猜，不能算"先问"的功劳。
- **"必须先澄清"的口径：** 判分代码一开始在模拟用户模式下忽略了"必须先反问"的要求，会把猜对的运行也算成功（改造前会显示 83%）。已修正为仍要求先反问，所以上表任务成功率是 50% → 88%，"必须先澄清"类是 17% → 67%，和第 1 节一致。

**局限：**

- 扮演用户的和被测 Agent 是同一个模型，可能"自己配合自己"；
- 意图是出题时定的；
- 判分是关键词匹配，一个把很多角度都列出来的回答也可能碰巧命中；
- 每个版本只有 16 次运行。

## 3. 计划随出图自动推进

改动：画出一张图后，由代码把计划里对应的步骤标为完成、下一步标为进行中，模型不再为了更新状态单独调用 `update_plan`。用 `ALIDADE_PLAN_AUTO_ADVANCE=0` 关掉做对照。

- 题目：4 道三步分析题（`planned`）× 2 次，`-Jobs 1`；
- 结果目录：`new-advance-off`、`new-advance-on`；对比报告：`compare-advance.md`。

| 指标 | 模型自己更新状态 | 自动推进 | 变化 |
|---|---|---|---|
| 成功率 / LLM 评分 | 100% / 5.00 | 100% / 5.00 | = |
| 平均 update_plan 调用次数 | 2.2 | 1.1 | −50% |
| 平均 LLM 调用数 | 7.5 | 6.4 | −15% |
| 平均总 token | 110,602 | 90,612 | −18% |
| 平均未命中缓存的输入 token | 4,604 | 3,164 | −31% |
| 平均耗时（秒） | 24.4 | 22.5 | −8% |

update_plan 调用减少的次数（约 1.1 次/题）和 LLM 调用减少的次数基本相等。也就是说，省下的正是只为更新状态的来回，质量没有变化。耗时差距只有 8%，样本又只有 8 次，引用时以调用数和 token 为准。

## 4. 并行子 Agent

改动：计划里互不依赖的步骤，交给各自独立的子 Agent 同时完成（独立的 Python 会话、动作预算、超时和失败隔离），最后由主 Agent 汇总。开关是 `ALIDADE_SUBAGENTS`，默认关闭。

- 题目：多角度题 4 道、多步题 8 道，各 2 次，`-Jobs 1`；
- 结果目录：`new-sub-off2`、`new-sub-on2`；对比报告：`compare-subagents.md`。

| 指标 | 单 Agent | 子 Agent |
|---|---|---|
| 成功率 / LLM 评分 | 100% / 4.88 | 100% / 4.88 |
| 多角度题：平均耗时（秒） | 16.1 | 20.7（+29%） |
| 多角度题：平均 LLM 调用数 | 4.9 | 9.4（+92%） |
| 平均未命中缓存的输入 token | 1,997 | 3,863（+93%） |
| 多角度题：计划里有可并行步骤的比例 | 0% | 88% |
| 子 Agent 总数 / 失败率 | — | 14 / 0% |

功能是对的：模型能识别出可以同时做的步骤，子 Agent 全部成功，结论也没有变差。但它变慢了，原因是固定开销大于节省的时间。以 `multi-movies` 为例：

- 单 Agent 整题 11.6 秒，看一次数据，接着画两张图；
- 开子 Agent 时，两个子 Agent 确实同时跑，但每个各要约 9.5 秒，因为都要从头看数据、画图、写小结，约 3 次调用；
- 前面还要多一次列计划，后面还要多一次汇总，总共 15–21 秒；
- 子 Agent 的提示词前缀和主 Agent 不同，用不上前缀缓存，所以未命中缓存的输入 token 几乎翻倍。

deepseek-flash 每次调用只要 2–3 秒，两步并行最多省掉一张图的时间。只有在每一步都很重（多次查询、多张图），或者模型单次调用很慢时，并行才可能划算。因此开关保持默认关闭。

可能的改进（未做）：

- 把主 Agent 已经看过的表结构直接交给子 Agent，省掉重看数据；
- 只在 ≥3 个、且每步都较重的步骤时才拆。

另外，测试中发现并修复了一个问题：用户点"停止"后，正在运行的子 Agent 会继续调用模型直到结束。现在停止时会先通知所有子 Agent，它们在下一次调用模型之前停下。

## 5. 过度反问：问题有一部分不在数据里

问题：`grounding-stocks-2024` 问"AAPL 在 2024 年全年涨了多少"，但数据只覆盖 2025-07 到 2026-01。Agent 会反问"接下来怎么做"，并把"加载 2024 年数据"作为推荐选项。评测脚本自动选了推荐项，于是进入加载数据的流程，又追问数据放在哪里，最后停在等待回答的状态。

修法分两步，都在核心技能说明里：

1. 问题有一部分超出已有数据时，不要停下来问，直接说明缺什么，给出数据能支持的最接近答案，再提一句可以帮忙加载；
2. 不要把"加载缺失数据"放进反问选项，更不能作为推荐项，由用户看完回答后再决定。

| 版本 | 直接回答 | 平均 token |
|---|---|---|
| 只有第 1 条（`new-aapl`） | 2/3 | 63,956（失败的那次 134,395） |
| 两条都有（`new-aapl2`） | 5/5 | 30,194 |

回答示例："`stock_history` 只覆盖 2025-07-31 至 2026-01-26……在这段区间内 AAPL 从 207.13 升至 255.41，约 +23.3%。如果需要 2024 年全年涨幅，我可以帮你接入数据源。"

## 6. 数字溯源检查

本轮各组里"找不到出处的数字"共 3 个，逐个核对：

| 数字 | 判断 | 处理 |
|---|---|---|
| `clean-sales-avg` 的"把缺失当 0 时约 $462.2" | **真问题**：模型没有计算就给了一个估计值，用数据实际算出来是 $461.88 | 检查器抓得对 |
| `clarify-movie-success` 的"前 15 名" | 误报：这是作者选的名次范围，不是从数据里得出的结论 | 跳过"前 N / top N"，"共 523 名用户"这类人数仍会检查 |
| `planned-gas` 的"90 年代" | 误报：年代 | 跳过"N 年代" |

## 7. 简历可用的表述

> 为数据分析 Agent 设计"澄清优先"流程和数据体检：在 13 道难题上，出图前先澄清的比例从 6% 升到 75%，用户确认方向前的 token 降低 54%，数据清洗题正确率从 80% 升到 100%。用 LLM 模拟带隐藏意图的用户评测：按用户真实意图答对的比例从 75% 升到 100%，同时总 token 降低 31%。

> 计划进度改为随出图由代码自动推进，三步分析任务的 LLM 调用减少 15%、token 减少 18%，正确率不变。

> 实现了计划步骤的依赖识别和并行子 Agent（会话隔离、超时与失败隔离、可中断）。实测在双角度问题上反而慢 29%，原因是子 Agent 冷启动和汇总的固定开销大于并行节省的时间，因此保持默认关闭。

引用时注明模型（deepseek-flash）和样本量（13 题 × 2 次、8 题 × 2 次、4 题 × 2 次），以及模拟用户评测的局限。

## 复现

```powershell
# 1. 先澄清 / 数据清洗
.\eval\eval.ps1 new -Only ambiguous,clarify,cleaning -Tag focus-clean
python eval/report.py eval/results/old-focus eval/results/new-focus-clean --labels 改造前 改造后

# 2. 模拟用户
.\eval\eval.ps1 new -Only ambiguous,clarify -UserSim -Tag usersim
.\eval\eval.ps1 old -Only ambiguous,clarify -UserSim -Tag usersim
python eval/report.py eval/results/old-usersim eval/results/new-usersim --labels 改造前 改造后

# 3. 计划自动推进
$env:ALIDADE_PLAN_AUTO_ADVANCE = '0'; .\eval\eval.ps1 new -Only planned -Jobs 1 -Tag advance-off; Remove-Item Env:ALIDADE_PLAN_AUTO_ADVANCE
.\eval\eval.ps1 new -Only planned -Jobs 1 -Tag advance-on

# 4. 子 Agent
.\eval\eval.ps1 new -Only multiangle,multistep -Jobs 1 -Tag sub-off2
$env:ALIDADE_SUBAGENTS = '1'; .\eval\eval.ps1 new -Only multiangle,multistep -Jobs 1 -Tag sub-on2; Remove-Item Env:ALIDADE_SUBAGENTS

# 5. 数据不全的问题
.\eval\eval.ps1 new -Only grounding-stocks-2024 -Repeat 5 -Tag aapl2
```

`report.py` 每次都会按最新的判分规则重新评分，所以第 2 节的数字可以直接从原始结果重新生成。
